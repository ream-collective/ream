# Progressive SSZ dependencies and fork-aware roots

Ream uses sigp's progressive SSZ implementation as the foundation for
[EIP-7688](https://github.com/ethereum/EIPs/blob/f2e6d7fb01194d590e16fcdcae8061d06cf1a7f1/EIPS/eip-7688.md).
This dependency change makes progressive hashing, lists, bitlists and container
derives available. Consensus types still use their existing serialization and
hashing rules; migrating fork types and implementing ePBS are separate changes.

## Dependency pins

The workspace patches the trait crates and their derives together, so transitive
users, including the lean dependencies, share the same `Encode`, `Decode` and
`TreeHash` traits.

## APIs available for migration

- `tree_hash::ProgressiveMerkleHasher`: stream packed bytes or element roots with
  `write`, then call `finish`. It implements the EIP-7916 subtree structure.
- `ssz_types::ProgressiveVariableList<T>`: the default has no context-specific
  length limit. `new(Vec<T>)`, `TryFrom<Vec<T>>` and `push` return `Result`; it is
  not an infallible `From<Vec<T>>` replacement. Basic types are packed, composite
  elements contribute their roots, and the element count is mixed in.
- `ssz::ProgressiveBitList`: imported from `ethereum_ssz`'s Rust crate name `ssz`.
  `with_capacity(len)` returns the bitlist directly. Its root mixes in the bit
  count, excluding the serialization delimiter from the hashed data.
- `tree_hash_derive::TreeHash` supports progressive containers:

```rust,ignore
#[derive(TreeHash)]
#[tree_hash(struct_behaviour = "progressive_container", active_fields(1, 0, 1))]
struct Example {
    first: u64,
    third: ProgressiveVariableList<u8>,
}
```

An inactive position contributes a zero chunk without adding a serialized field.
The active-fields bitvector is mixed into the container root. List and container
encodings remain the same as the corresponding ordinary types with the same
fields and values.

`ProgressiveVariableList<T, N>` also supports an optional implementation limit.
That limit does not affect the root, but it rejects values during construction or
decoding. Choose bounds separately from consensus operation validation; retaining
an old `VariableList` cap automatically would change which values can be decoded.

## Fork-aware roots: proposed migration rule

Keep pre-Gloas types and roots intact. Introduce the new fork's types with
progressive fields and derives, and dispatch to the appropriate representation
at the fork boundary. Every nested growing list must use the corresponding root
rule; changing only the outer container's hasher is insufficient.

For shared storage such as the state cache, make the hashing scheme explicit
and derive it from the state's fork version. Block and message roots must use
the fork context of their enclosing slot or protocol before signing or verifying.
This is a proposal for subsequent migration work, not an activated fork rule.

## Validation

Run the self-contained integration checks:

```sh
cargo check --workspace --locked
cargo test --locked --profile dev -p ream-consensus-beacon --test progressive_ssz
```

The tests compare sigp's streaming roots against an independent materialized
SHA-256 tree, and check packing, nested list offsets, bit delimiters, inactive
fields, and serialization compatibility. They do not establish full Gloas
conformance.

With the Fulu fixtures installed as described in
[`testing/ef-tests/README.md`](https://github.com/ream-collective/ream/blob/master/testing/ef-tests/README.md), check existing
consensus serialization and roots:

```sh
cargo test --locked --profile dev -p ef-tests --features ef-tests --test tests test_type
```

The existing runner checks Fulu types. Progressive Gloas `ssz_static` and
`ssz_generic` vector coverage remains part of the subsequent type migration.
